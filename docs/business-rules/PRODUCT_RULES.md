# Product rules — Madfu merchant onboarding

> Generated by `npm run docs` from the prototype source (`src/`). Do not edit by hand.

Source files: `src/rules/config.ts` (policy values), `src/rules/categories.ts` (fixture catalogue), `src/rules/decisions.ts` (pure decision functions), `src/journeys/engine.ts` (state machine). Values marked *provisional* are assumptions — see [DECISION_LOG.md](DECISION_LOG.md).

## 1. Applicant types and entry

- Two applicant types share one entry page (S01): **Registered Business** (CR number) and **Freelancer** (National ID). The freelancing certificate number is **not** requested at entry.
- All four fields are mandatory. Changing applicant type resets the identification field and every identity-dependent verification; changing the mobile resets OTP.
- Once a Nafath request has been sent, applicant type and identification become read-only (provisional D-14).

Frontend **structural** validation only (configurable placeholders — not government validation):

| Field | Rule | Message |
| --- | --- | --- |
| Commercial Registration Number (CR) | /^\d{10}$/ | Enter a valid Commercial Registration number (10 digits). |
| National ID Number | /^[12]\d{9}$/ | Enter a valid National ID number (10 digits). |
| Mobile | +966 /^0?5\d{8}$/ | Enter a valid Saudi mobile number, e.g. 5X XXX XXXX. |
| IBAN | SA + 22 digits + ISO 13616 mod-97 | Enter a valid Saudi IBAN |

## 2. Existing-account detection (backend, no extra screen)

1. **Check 1 — identity** (CR or National ID). If it exists → S01-X “An account already exists with these details.” The application stops and **Check 2 is skipped**.
2. **Check 2 — mobile** runs only for a new identity. Linkage to other accounts is recorded (`MOBILE_LINKED_TO_OTHER_ACCOUNTS`) for matching / risk, and **never blocks**.

| Example | Result |
| --- | --- |
| Mobile A + CR 1 | Allowed |
| Mobile A + CR 2 | Allowed |
| Mobile A + National ID 1 | Allowed |
| Same CR again | Not allowed |
| Same National ID again | Not allowed (adding another certificate = future flow S01-F, pending specification) |

## 3. OTP

| Rule | Value |
| --- | --- |
| Max incorrect attempts | 3 (confirmed) → S02-L |
| Code length | 6 |
| Expiry | 120s (provisional) — expired code does not consume an attempt |
| Resend cooldown / max | 30s / 3 (provisional) |
| Resend resets attempts | false |

Real SMS is never sent; the code is never shown in the customer UI. A labelled development simulator triggers success, failure and expiry.

## 4. Revenue routing (after OTP)

| Band | Range | Registered Business | Freelancer |
| --- | --- | --- | --- |
| Below SAR 100,000 | < 100,000 | SALES_LEAD | SELF_ONBOARDING |
| SAR 100,000 to SAR 20,000,000 | ≥ 100,000 and ≤ 20,000,000 | SELF_ONBOARDING | SELF_ONBOARDING |
| Above SAR 20,000,000 | > 20,000,000 | SALES_LEAD | SELF_ONBOARDING |

Exactly SAR 100,000 is treated as self-onboarding (provisional D-01). The CR sales-lead journey saves the application and shows Outcome C; it never requests authorized persons, Nafath, IBAN, VAT, channels or a contract.

## 6. Registered Business — government CR verification

| Result | Behaviour |
| --- | --- |
| Valid | Show business details → S05 |
| Expired | Notice; may proceed; flag CR_EXPIRED |
| Not found / invalid | Cannot proceed; “Edit CR number” → S01 |
| Temporarily unavailable | 2 silent automatic retries, then up to 3 manual retries, then save-and-exit (provisional D-08) |
| Unexpected provider error | Generic error with retry and support |

Authorized-person data is never fabricated when the API fails.

## 7. Registered Business — authorized persons

- Only **individuals** are shown (companies and other entities are filtered out).
- Masking: first and last names visible, second and third names masked; National ID first 3 and last 3 digits visible.
- Exactly one selection; Continue is disabled until one is chosen. A single individual is pre-selected but still confirmed.
- No eligible individual → manual-review path: continue to business details, Nafath not possible, contract disabled (Outcome B).

## 8. Nafath

- Maximum **2 attempts per application**, shared across individuals. Changing the selected person never resets the counter.
- Outcomes: verified, rejected, timed out, technical failure. Technical failure (request not created) consumes an attempt: **false** (bounded at 3; provisional D-11).
- After the 1st unsuccessful attempt: retry, or (CR) choose another authorized person; remaining attempts are shown.
- After the 2nd: Nafath marked unverified, manual verification required. CR continues to business details; Freelancer continues to manual certificate entry. **Contract signing is not permitted.**
- Freelancer Nafath targets the National ID entered at S01. On success, certificates are retrieved (S07).

## 9. Business details and IBAN

- IBAN format (structure + mod-97) must be correct regardless of verification outcome. Format ≠ ownership.
- Ownership check runs asynchronously when the field is left; an unchanged value is never re-checked; editing invalidates the previous result.
- Match target: CR → registered business; Freelancer → individual National ID. Freelancer without successful Nafath → **no ownership API call** (CR without Nafath: not called, provisional D-12).
- Max **2 unsuccessful** ownership checks; after that the applicant continues and the IBAN is queued for manual financial verification.
- Provider technical errors are modelled separately; after 3 the status becomes *pending (provider)* — not a failed check (policy pending, D-10).
- VAT: Yes → VAT number required. Channels: Online → website; Offline → Google Maps link for one branch; Both → both. Branch count optional.

## 10. Contract eligibility

| Nafath | IBAN ownership | Contract |
| --- | --- | --- |
| Verified | Verified | Allowed |
| Verified | Failed twice | Allowed |
| Verified | Pending / technical issue | Allowed subject to required processing rules |
| Not verified | Any | Not allowed |

Provisional additional blocking review flags: `CERT_EXPIRED`, `CERT_INCONSISTENT`, `CERT_NOT_FOUND_MANUAL_ENTRY`, `CERT_MANUAL_ENTRY_UNVERIFIED`, `NO_ELIGIBLE_AUTHORISED_PERSON`.

The contract screen is a generic placeholder; acceptance is simulated and not legally binding (D-02). Decline keeps the application saved but not submitted (D-09).

## 11. Outcomes and internal statuses

| Outcome | Applicant sees | When |
| --- | --- | --- |
| O-A | Your application has been submitted successfully. | Nafath verified + simulated contract acceptance |
| O-B | Thank you. Your application has been received. Our team will contact you if any additional information is needed. | Details completed without successful Nafath, or with a blocking review flag |
| O-C | Thank you for your interest in Madfu. Our team will contact you. | Revenue lead, restricted / review category, restricted certificate |

Internal statuses (never displayed): SALES_LEAD, CATEGORY_REVIEW_REQUIRED, NAFATH_MANUAL_VERIFICATION, IBAN_VERIFICATION_PENDING, CR_EXPIRED, CERTIFICATE_REVIEW_REQUIRED, CONTRACT_PENDING, CONTRACT_ACCEPTED, APPLICATION_SUBMITTED. No approval, activation or commercial eligibility is ever stated.

## 12. Persistence and resume

Tracked per application: ID, applicant type, identification, revenue band, mobile verification, category, government result, selected person, Nafath attempts/result, certificate, business details, IBAN counters/result, contract state, current step, review flags, submission state, audit log and paid-call ledger. Demo persistence uses browser storage with synthetic data only; refresh never loses progress; submitted applications cannot be resubmitted.
